# Android 模拟器操纵与输入需求

## 用下来卡在哪里

现有 Android 调试桥（Android Debug Bridge，ADB）已经能安装、启动应用，点按、滑动、截图和读取日志。这些基础能力够用，不需要重做模拟器。

真正阻碍独立验收的是：Tauri WebView 在当前 `uiautomator dump` 中只显示一个根节点，脚本无法按“按钮名称／输入框名称”找到网页控件；`adb input text` 也不能可靠输入中文、换行和较长的混合文本。结果只能看截图猜坐标、操作虚拟键盘，录入与设置页难以稳定复测。

## 需要补的交互接口

1. **找到并操作控件**：能读取 WebView 内控件的名称或测试标识、类型、可见与可用状态、位置；按这些信息点按、聚焦、滚动到控件并等待它出现。同名控件可限定在指定对话框或卡片内。实现可用无障碍节点或 WebView 调试接口，不要求固定技术方案。
2. **直接输入并读回文本**：对指定输入框执行清空、替换、追加或粘贴，支持中文、英文、换行、标点和长文本；输入后触发应用正常的输入事件，并能读回完整值核对。不要求逐字点击虚拟键盘。测试密钥的值不得写入操作日志。
3. **保留基础操作的可靠回退**：语义定位暂不可用时，允许根据当前截图和控件边界做坐标点按；工具应同时返回屏幕尺寸与点击结果，避免把固定坐标当成长期脚本。

## 怎么判断补好了

在真实 Android WebView 中，脚本无需人工介入即可找到录入页输入框，写入含中文、英文、换行和标点的长文本并逐字读回；随后按名称进入第二步表单、填写一个义项并点按保存。切换到不同屏幕尺寸后，同一脚本仍能定位并操作这些控件。做到这一步，现有 ADB 的安装、截图和日志能力就足以支撑后续业务验收。

## 已确认的工具路线与优先级

- 设备底座使用 Google Android Emulator；Android 调试桥（Android Debug Bridge，ADB）负责模拟器发现、安装包部署、启动和底层诊断。
- 控制层可使用 Appium 官方 UiAutomator2 驱动与已有 Test Android App 工具。两种模型上下文协议（Model Context Protocol，MCP）工具均可使用；按当前验收路径选操作更直接、成本更低的一种，必要时结合 Android 调试桥，不预设必须由单一工具完成。
- 保留两套环境共存。分别记录实际可用能力和证据，不以任一工具未覆盖某项能力阻断其他方式可完成的业务验收。
- **P0：直接输入文本。** 用 `appium_set_value` 对语义定位到的输入框设置完整字符串；覆盖中文、英文、换行、标点和长文本，并读取同一输入框的实际值逐字核对。
- **P1：Tauri WebView 语义访问。** 可用 `appium_context` 列出并切换至 `WEBVIEW` 上下文，再尝试文档对象模型（Document Object Model，DOM）定位器；层叠样式表（Cascading Style Sheets，CSS）选择器也可使用。须在本项目 Android 应用中验证能力，不能以普通原生页面或工具清单存在该功能代替。用户已确认 DOM 定位不是当前实现与用户级验收的强阻塞条件；若失败，改用可用的设备操作与完整屏幕截图，逐项记录实际覆盖范围。

新旧能力对照至少覆盖模拟器与设备发现、应用安装和启动、控件读取与定位、点按与滑动、直接文本输入、截图、日志、返回导航及设备状态。对照时区分“由 Appium MCP 直接提供”“仍由 ADB 提供”和“目前缺失”，避免把底层命令可用误报成 MCP 工具覆盖。
