# V2 首轮自主判断与口径收敛

- 记录轮次：第一轮自主实现（2026-09-19 夜间连续执行）。
- 性质：本轮无 grill-me / 会话确认环节，以下全部判断由 agent 自主收敛并直接执行，**供用户晨审**。
- 效力边界：晨审通过前，本文件判断**不回写** `docs/需求规格.md`、`docs/复习调度算法.md`、`docs/界面设计规格.md` 三份继承规格；与本文件冲突的既有继承口径以继承规格为准，本文件只新增继承规格未覆盖的部分。
- 标注约定：**【用户已定调】** = 用户指令明确给出，agent 只落实；**【建议默认落实】** = 技术决策文档或继承规格给出建议，agent 选择落实；**【自主判断】** = agent 自主决定，晨审重点审查项。
- 每条包含：判断、理由、影响范围、可逆性。

## A. 设置同步口径 triage（最先执行的判断）

### A0. triage 框架【用户已定调】

- 大语言模型服务配置（Base URL / 模型 / API Key / 思考开关）**不同步**，每设备各配。
- 凡涉及学习调度的设置（每日目标、复习参数、目标保持率、学习日换日边界等）**倾向同步**。
- 凡判定同步者，**云端（服务器库）是唯一权威数据源**。

### A2. Space 级设置走 settings KV 通道，不新增"设置变更"领域事件【自主判断】

- 判断：`space.<spaceId>.*` 键进入 settings 通道（服务器哑 KV 存储），不定义 `spaceSettingsUpdated` 之类新学习事件。
- 理由：需求规格 7.2 事件类型清单不含设置类事件，继承规格口径不动；服务器 settings 通道本就是无语义 KV 存储，加命名空间前缀即可承载 Space 级设置；LWW 收敛简单确定。
- 影响范围：protocol settings schema 的键命名约定；Phase 2 迁移把 V1 `space_learning_settings` 行转为对应 KV 条目。
- 可逆性：若晨审要求改为事件承载，需新增事件类型并修改重放逻辑，成本中等，上云（Phase 2）前定稿即可。

### A3. Space 删除后遗留孤儿 settings 键可接受【自主判断】

- 判断：不实现孤儿键清理。
- 理由：服务器必须保持哑（不认识 space 概念、不懂键语义），清理逻辑若放服务器就违反哑服务器边界；个人自用规模下遗留几条孤儿键无实际危害，客户端可忽略未知键。
- 影响范围：无功能影响；键空间微增。
- 可逆性：高，未来可在客户端发起"删除键"扩展协议。

### A4. 智能整理可用性 = 本地开关 × 本地 LLM 配置【自主判断】

- 判断：`features.smartOrganizing`（同步）与每设备 LLM 配置（本地）组合出各设备的实际可用性；本地开关开但该设备未配密钥时，整理入口降级为"未配置"（与继承规格 6.9 行为一致）。
- 影响范围：设置页语义（后续 UI 阶段）；本轮仅体现为两路存储分离。
- 可逆性：高。

### A5. 设备本地设置预留【自主判断】

- 判断：客户端本地 KV 存储自本轮起存在，本轮只定义机制不定义 UI 键；未来 UI 主题、窗口状态等走本地 KV。
- 可逆性：高。

## B. 协议与同步语义判断

### B1. settings 数据模型与 LWW 定稿【建议默认落实】

- 判断：settings 条目为 `{ key, value, updatedAt, deviceId }`；value 统一为 JSON 可序列化值。服务器逐键 LWW 合并：`updatedAt` 大者胜；`updatedAt` 相等时 `deviceId` 字典序大者胜（确定性 tie-break，任意顺序合并结果一致）。
- 理由：技术决策文档建议 LWW（值 + `updated_at` + `device_id`）；tie-break 选 deviceId 字典序而非"后到者胜"，因为服务器收到顺序不确定，字典序保证收敛结果与到达顺序无关（可重放、可测试）。
- 影响范围：protocol settings schema、server 合并逻辑、客户端 settings 仓库。
- 可逆性：中——上云前可改，上云后收敛规则变更需全端升级。

### B2. settings 与事件通道完全分离【自主判断】

- 判断：学习事件 append-only 永不覆盖；settings 可被 LWW 覆盖；客户端 settings 变更同样走 outbox 异步推送、失败退避重试，但不进入事件流、不参与领域重放。
- 理由：两者收敛语义根本不同（append-only 重放 vs 覆盖合并），混流会让重放器被迫理解 LWW。
- 可逆性：中。

### B3. 领域重放排序按技术决策执行【建议默认落实】

- 判断：排序键 `occurredAt → deviceSeq → deviceId → eventId`（末级 tie-break 同时用 deviceId 与 eventId，杜绝并列）；protocol 导出统一比较函数，服务器与客户端不各自实现排序。
- 理由：`docs/V2迁移技术决策.md` 第四章明文；`serverSeq` 仅作同步游标，禁止进入排序。
- 可逆性：低（本就是定稿口径，此处是落实）。

### B4. 事件 schema 以 V1 事件表为基、加同步字段【自主判断】

- 判断：V2 事件同步字段 = V1 `learning_events` 既有字段（`id/event_type/target_type/target_id/occurred_at/learning_day/source/metadata_json`）+ 新增 `deviceId`、`deviceSeq`；`serverSeq` 仅由服务器分配与下发，push 载荷不含。事件类型枚举 = 需求规格 7.2 全部条目（逐项展开后为 **18 类**，`testSessionPaused/Resumed`、`dictionaryFetched/FetchFailed` 为成对条目；B4 初稿写"15 类"系笔误，M1 实现时按规格原文核对修正），protocol 以 Zod enum 固化。
- 理由：继承规格 7.2 是事件语义真理源；V1 事件表是既成事实的字段形态；同步三字段为技术决策第四章要求。
- 可逆性：中——schema 变更需协议兼容测试同步改。
- M1 落地补充：事件信封字段严格校验，各类事件 payload（对应 V1 `metadata_json`）取"已知字段强类型 + 未知字段 passthrough 保留"策略；`taskDeferred` 在 V1 仅有枚举定义无构造点，payload 暂为开放 record，待 domain/application 移植时收紧。

### B5. deviceId 生成与形态【自主判断】

- 判断：每设备首次启动生成 UUIDv4 作为 deviceId，持久化于本地库；无注册机制、不占协议字段（只作为事件/settings 条目的属性传输）。
- 理由：个人自用无账号系统；UUID 冲突概率可忽略。
- 可逆性：高。

### B6. 时间戳来源与已知限制【自主判断】

- 判断：事件 `occurredAt` 与 settings `updatedAt` 均由**客户端可注入时钟**生成（UTC ISO8601 绝对时间）；服务器只记录自己的接收时间且不参与任何领域排序。已知限制：设备间时钟偏差会轻微影响 LWW 公平性——个人自用场景可接受，不做时钟同步机制。
- 理由：AGENTS.md"时间计算必须通过可注入时钟"约束 + 技术决策"日期持久化使用绝对时间"。
- 可逆性：中。

### B7. API 错误语义【自主判断】

- 判断：401 = Bearer 鉴权失败；400 = schema 校验失败（响应体附 Zod 错误摘要）或查询参数非法；push 中重复 `event_id` 不报错，逐事件返回 `duplicated: true`（幂等成功）；不使用 409/416。所有错误响应统一 `{ error: { code, message } }` 形态。
- 理由：幂等语义下"重复"不是冲突而是正常重放；错误形态统一利于客户端单点处理。
- 可逆性：高。

### B8.【晨审关注】V1 存在规格外事件类型，本轮未纳入协议

- 事实（M1 实现中发现）：V1 已实现 `wordManuallyMarkedUnmastered` / `wordManuallyMarkedMastered` 两个事件类型（"手动不认识/掌握标记"，对应需求规格验收场景 10 与核心概念"手动不认识反馈"），但 7.2 事件类型清单未收录二者——规格与 V1 实现不一致。
- 判断：protocol 枚举严格按 7.2 十八类固化，未擅自纳入规格外事件。
- 影响与风险：Phase 2 迁移 V1 真实数据时若存在这两类历史事件，将被 schema 拒绝。
- 建议晨审定夺：扩枚举（推荐，语义在核心概念表已有定义）或迁移时降级转换；在此之前不动 7.2 口径。

### B9.【晨审关注】`wordContentUpdated` 的规格要求与 V1 实现不一致

- 事实：规格 7.2 要求该事件"保存修改前后值和二次确认标记"；V1 实际 metadata 仅存 `{ normalizedKey }`。
- 判断：protocol 按 V1 现状字段固化并 passthrough 保留未来字段，未擅自补写规格要求的字段（避免伪数据）。
- 影响：领域重放侧（domain/application）无法从现有事件还原修改前后值；这是 V1 既有数据缺陷，不是 V2 移植引入。
- 建议晨审定夺：V2 起该事件是否按规格补全字段（推荐），历史数据按原值迁移。

## D. 服务器实现判断

### D1. 鉴权形态【自主判断】

- 判断：单用户静态 Bearer token，由服务器启动配置（环境变量/本地配置文件）提供；本地测试用随机生成 token；token 及其样例不进仓库。
- 理由：技术决策"个人自用第一版无需账号系统，直接 Base URL + Bearer access token"。
- 可逆性：高（未来换真实 token 只是配置变更）。

### D2. settings API 形态【自主判断】

- 判断：`GET /settings` 返回全量 KV（含每键 `updatedAt`/`deviceId`）；`PUT /settings` 接受批量条目数组，服务器逐键 LWW 合并后返回合并结果。settings 不引入版本游标——每次全量对账，个人规模数据量极小。
- 理由：哑服务器 + 简单收敛；全量对账规避"settings 游标"复杂度。
- 可逆性：上云前可改。

### D3. 备份方式【建议默认落实】

- 判断：备份脚本使用 better-sqlite3 在线 backup API 生成带时间戳副本文件，禁止直接复制正在写入的 db 文件（与 AGENTS.md 真实数据迁移闭环一致）。
- 可逆性：高。

### D4. gzip 传输【建议默认落实】

- 判断：push 请求体接受 `Content-Encoding: gzip`；pull/settings 响应按 `Accept-Encoding` 压缩（Fastify 压缩插件）；批量端点单往返。
- 理由：技术决策附录"弱网传输"硬性要求。
- 可逆性：高。

### D5. 服务器库 schema【自主判断】

- 判断：`events` 表把同步字段物化为列（`event_id` PK、`device_id`、`device_seq`、`occurred_at`、`event_type`、`server_seq` 自增唯一），事件 payload 整体以 JSON 文本存储——服务器校验 protocol Zod schema 但不解读业务语义；`settings` 表（`key` PK、`value_json`、`updated_at`、`device_id`、`server_updated_at`）。`server_seq` 由单事务内计数器保证严格单调。
- 理由：物化列服务于去重与增量查询；payload JSON 化保证服务器零业务逻辑。
- 可逆性：中——上云前可改表结构，上云后按迁移闭环处理。
