# 录入静默失败故障报告与基础日志设计

> 本文档承载两件事：一是 2026-09-07 正式环境实测发现的「智能整理静默失败」故障报告与修复方向；二是全应用基础日志能力的范围设计。修复实施另行排期，本文档只收敛口径。

## 实施确认

2026-09-07，用户已确认本报告进入自主执行：修复词书模式智能整理失败被误报为成功的问题，加入基础落盘日志，使用用户提供的真实批量转写材料在独立验收数据根目录执行桌面验收，并重新构建新的应用包。验收不得连接正式学习数据库；日志不得记录原文全文、API Key、环境文件或其他外部服务凭证。

用户追加确认：真实大语言模型整理是该功能的主要使用路径；本轮用户级验收必须使用用户已配置的 API Key 对上述真实批量转写材料执行一次真实整理，确认能够进入检查页并展示实际候选条目。手动填写只能作为网络失败时的降级能力，不能替代真实整理主路径验收。

由于 SQLite 连接绑定创建线程，整理工作线程不得直接写数据库。本轮采用“整理阶段显式传播结构化失败，主线程在收到失败后保存解析失败草稿，再驱动 UI 失败路径”的等价实现；同步便捷入口继续返回带失败原因的结果，以保持既有应用层调用兼容。

2026-09-07 真实桌面验收进一步发现：百炼模型卡将 `deepseek-v4-flash-0731` 标为“不支持结构化输出”，该快照在本项目 `entry-organizer-v3` 整理请求中两次实际返回 HTTP 200 但空正文。实现已对旧快照兼容地省略 `response_format`，并将新安装默认模型改为官方支持结构化输出的 `deepseek-v4-flash`；提示词中的 JSON 契约和本地严格校验保持不变。使用同一已配置 API Key 和 16 词真实转写重启验收应用后，请求于约 67 秒以 HTTP 200 成功返回，生成 17 个候选并进入步骤二检查页。

2026-09-07 用户最新确认：整理请求收到的模型响应正文必须原样写入应用日志。该证据用于直接判断空正文、字段变形、截断或供应商非标准响应；日志仍不记录请求头、API Key 或请求体。

同日用户进一步确认：整理请求不设置客户端主动超时；整理进行中主按钮显示“取消整理”，再次点击由用户主动结束当前请求。因网络连接中断等外部错误产生的失败仍按网络失败路径处理，但不存在应用自行触发的“超时失败”。

## 第一部分：录入静默失败故障报告

### 现象

2026-09-07，用户在正式应用中用词书模式（必考词 Space，Unit 1 / List 1）录入一段 16 个词条的语音转写，点击「智能整理并检查」一次。界面提示「已整理，请检查下方词汇」并进入第二步表单页，条目数为 0，全程没有任何错误提示；用户未手动进入第二步。

### 证据

正式数据库 `first_pass_drafts` 唯一草稿行（只读查询获得，未改动数据）：

- `status = 解析失败`，`last_error = 大语言模型整理失败：大语言模型整理请求超时`
- `audit_json.interactionCount = 1`，`parserVersion = entry-organizer-v3-failed`，`candidates_json = []`

即大语言模型第一次请求在当时的 20 秒客户端超时处断开，整理实际失败；数据层记录诚实，界面层谎报成功。该数值属于故障发生时的旧配置，不是当前产品口径。

### 根因链

1. **触发**：故障发生时整理请求使用 20 秒客户端超时（`OpenAICompatibleOrganizerConfiguration.timeout_seconds`），长转写加思考型模型在该时限内无法完成；当前已移除整理请求的客户端主动超时，改由用户通过“取消整理”结束请求。
2. **应用层吞掉失败**：`FirstPassService.organize_prepared_draft`（`src/ebbinghaus/application/first_pass.py:266-277`）捕获 `LanguageModelOrganizationError` 后**不抛出**，构造零候选空结果并把原因写入 `fallback_reason`，正常返回。这是旧「本地解析降级」时代留下的兼容语义，在 v3 契约下已成错误行为。
3. **UI 盲信成功路径**：因为工作线程没有收到异常，发出的是 `succeeded` 信号；`_handle_parse_success`（`src/ebbinghaus/ui/pages/first_pass.py:682-723`）**从不检查** `FirstPassParseOutcome.fallback_reason`（字段存在且已填值），于是显示「已整理」、跳转第二步、渲染 0 个条目。既有失败路径 `_handle_parse_failure`（「智能整理没有完成……原文仍在，可以重试或改为手动填写」，停留第一步）完全没有执行。
4. **范围**：常规模式走 `organize_entries` 入口，失败会正常抛异常，此坑只存在于词书模式的三阶段（prepare/organize/finish）路径。
5. **加重因素**：`logs/` 目录为空，应用没有任何落盘日志，现场无法自查，只能靠直接查询数据库确诊。

### 修复方向（按优先级，实施前需用户确认范围）

1. **应用层失败必须传播**：`organize_prepared_draft` 捕获整理异常后，先把失败状态与审计写入草稿（保证原文可恢复），然后**重新抛出**，使 UI 走既有失败路径。`_empty_parse_result` 仅保留给手动填写。
2. **UI 双保险**：`_handle_parse_success` 开头检查 `outcome.fallback_reason is not None`，成立则转入失败提示、绝不进入第二步；即使应用层将来再漏判，界面也不得谎报成功。
3. **取消客户端主动超时**：不再用 120 秒等固定时长替用户结束整理；工作线程登记活动 HTTPS 连接，用户点击“取消整理”时关闭该连接并回到步骤一。网络错误仍必须显性可见。
4. **补落盘日志**：见本文档第二部分。
5. **回归测试**：词书模式整理超时/失败的集成测试断言「草稿 = 解析失败且 UI 收到异常而非空成功」；UI 测试断言 `fallback_reason` 非空时停留第一步且不渲染第二步。

### 验收标准

- 复现路径（同一段转写或人为注入网络错误）下，界面停留在第一步，显示失败原因与「重试／改为手动填写」选择，原文不丢失。
- 用户点击“取消整理”后，必须立即关闭当前 HTTP 请求并回到第一步，原文保留；界面不得等待后台线程收尾，用户可以立即发起下一次整理。旧请求晚到的成功或失败结果必须丢弃，不显示网络失败或“解析失败”提示，也不生成失败草稿。
- 任何整理失败（网络、鉴权、结构修复耗尽）都不会出现「成功提示 + 零条目进第二步」；客户端不主动制造超时失败。
- 全量自动化测试保持通过，新增上述回归测试。

## 第二部分：基础日志设计

### 目标与原则

- 目标：现场可诊断。用户或开发者凭日志能回答「发生了什么、为什么失败、用的是哪份配置与算法版本」，不再依赖直接查询数据库。
- 日志是诊断手段，不替代既有业务事实源：草稿审计（`audit_json`）、不可变事件日志、调度可解释字段仍然以数据库为准；日志与之口径一致、互相可对照。
- 只保留必要内容，默认 INFO 级别，失败与异常记 ERROR；不追求全覆盖，禁止把日志当成第二份业务数据库。

### 位置与实现方向

- 路径由 `src/ebbinghaus/bootstrap/paths.py` 统一解析的 `log_directory`（正式运行与源码运行各自的数据根目录下 `logs/`），业务代码不得自行拼接路径。
- 使用标准库 `logging`，组合根（`bootstrap`）在启动期完成初始化；按日期滚动并限制单文件与总量（如每天一个文件、保留最近 14 天），避免无限增长。
- 各层通过 `logging.getLogger("ebbinghaus.<层名>")` 获取记录器；`domain` 与 `application` 只写纯文本事件，不得依赖具体输出目的地。
- UI 工作线程（整理、词典查询、连通性测试）中的异常必须先落日志再转换为界面提示，禁止静默退出。

### 必须覆盖的范围

1. **录入流程（步骤一与步骤二）**
   - 步骤一提交：学习模式、Space、Unit/List（词书）、原文长度、是否启用智能整理、整理配置标识（供应商类别、模型、提示词版本；**不含密钥**）。
   - 整理结果：成功时记录条目数、交互轮次、耗时和模型响应正文；失败时记 ERROR，包含用户可读原因、错误类别（网络／鉴权／结构校验）、交互轮次；用户取消单独记录为取消，不计为失败。取消由关闭底层连接实现，请求线程可能因此安静收到空响应体或截断内容而不是网络异常；这类迟到结果同样按取消记录，不得误报为“响应不是有效 JSON”等结构错误（2026-09-09 实测确认并修复）。
   - 步骤二保存：条目数、保存结果（成功／失败原因）；用户主动放弃或返回修改也记一条。
2. **调度算法**（呼应「调度器输出必须可解释」的既定规则）
   - 每日任务生成：输入状态摘要、到期原因、算法版本、最终任务数量。
   - 测试判断引起的状态演进：Word 状态迁移、FSRS 回写结果、掌握状态变化（含软掌握进入与自动撤销）。
   - 迁移、备份、单实例锁冲突等正式数据升级闭环关键步骤。
3. **后台系统必要项**
   - 网络请求状态：大语言模型请求开始／结束（HTTP 状态码、耗时、取消或网络错误）；整理请求的模型响应正文原样记录；在线词典并发查询的各源成败与缓存命中；连通性测试结果。
   - 启动与退出：数据根目录、应用版本、单实例锁获取结果。
   - 未捕获异常：全局钩子把崩溃前异常写入日志。

### 红线

- 绝不写入 API 密钥明文、`.env` 内容或任何外部服务凭证。
- 整理请求的模型响应正文按用户最新确认原样记录，便于直接诊断服务实际返回值；请求体、Authorization、API Key、`.env` 和外部服务凭证仍不得写入日志。用户原文不作为请求体之外的独立日志字段记录，业务事实由数据库草稿承担。
- 日志不承载业务流程判断：代码逻辑不得读取日志文件做任何决策。
- 日志文件与正式数据库一样不受 Git 跟踪，路径解析规则不变。

## 第三部分：2026-09-10 整理校验机制整改

### 背景

第一部分的失败传播修复落地后，整理链路不再静默失败，但正式使用实测（2026-09-09 至 2026-09-10）发现本地校验机制本身制造了新的误伤：

1. **重复证据消耗游标误追责**：证据定位按证据树顺序消耗重复片段的出现位置（隐含“每处原文只能被引用一次”）。原文中大量重复的“名词”等表述使引用配额耗尽，并把错误归咎给顺序靠后的无关词条（如实测中 conduct 被错误追责）。
2. **格式差异误判为订正**：`value` 与证据的比对只折叠大小写与空白，释义中半角逗号与全角逗号（如“组成,构成”与“组成，构成”）这类明确等价的形态差异被误判为“实质订正缺少 warning”。
3. **表示形式失败**：warning 空字符串、有效词性别名（`noun`、`名词`、`n`）未写成规范简称等纯表示差异被当作整批失败原因。
4. **错误归因混乱**：证据不存在、订正缺说明、结构缺失等不同原因混在同一句“类型或值无效”里，修复提示缺乏定位精度，模型多轮原样重犯。

同时确认：Extension 词条把证据引到错误位置属于真实错误——取消游标只解决 conduct 被错误追责的问题，不代表放行跨词条、跨义项的明显错误引用；无法唯一定位也不能直接等同于引用伪造。

### 整改口径（2026-09-10 用户确认）

- 删除重复证据的消耗游标：相同原文片段可支持多个字段，重复出现合法，高亮区间允许重叠、合并、去重；能按词条与释义上下文区分位置时优先使用对应位置；明显跨词条、跨义项的引用仍指出实际出错节点。
- 校验区分「格式规范化」与「实质订正」：有限、明确的等价规则（标点形态、大小写空白、词性别名）不要求 warning；错字订正、含义修改、无原文依据的补充仍必须实际订正并在同节点提供简体中文 warning。“名次”等错字不进入词性别名表，其含义由模型结合上下文判断。
- `warning` 缺失、空字符串、`null` 统一视为无警告；确实需要说明的节点不得静默放行；有效词性别名先本地规范化，不再整批失败；可选用法为空等表示差异由本地统一处理。
- 校验错误按词条汇总并至少分为四类：引用文本在原文中不存在、引用与当前字段上下文明显不对应、实质订正缺少同节点说明、必要内容或结构缺失；修复提示回显完整问题节点及其所属词条，删除“把 value 改回原文即可”的通用退路。
- 调用策略：一次完整整理 → 本地规范化与质量检查 → 局部修复（以完整词条为单位、客户端编号指定替换对象）→ 合并后整批复验 → 进入步骤二；最多 3 轮调用的上限保留，第二、三轮为局部修复；所有轮次保持思考开启；同一错误没有变化时必须更新定位与指引，不得原样重发。提速来源是更少的错误拒绝、更少的修复轮次和更小的修复请求，不是关闭思考、削减证据或漏填内容。
- 质量底线不降低：原文明示信息必须完整进入字段；明显错误必须实际订正；`source_excerpt` 保持原文字符；`source_excerpt: null` 只用于确实没有直接原文依据的内容；不得通过清空证据、删除义项、缩减内容、撤销正确订正或编造证据规避校验；修复耗尽后保留原文与本次成果并明确指出问题，不伪装完整成功进入步骤二。

完整产品口径以 `docs/需求规格.md` 6.2 为准。
