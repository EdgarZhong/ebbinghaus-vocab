# Ebbinghaus V2 技术栈迁移最终决策

- 状态：**已确认定稿**（2026-09-19 用户确认）。
- 效力范围：本仓库（Ebbinghaus-v2）全部实现工作。后续 Coding Agent 不需要重新做技术栈选型；唯一允许重开的例外是第七章 Tauri Android 闸门测试真实失败后启动的逃生路线。
- V1 仓库（`/Users/edgar/code/Ebbinghaus`，Python/PySide6）转为**只读行为规格、算法参考和数据迁移来源**；这是一次全量技术栈迁移重构，不是在旧项目上渐进修补，新实现不承担历史技术债。

现有 Ebbinghaus 是个人自用的英语学习/记忆管理客户端，核心是今日计划、词书/常规录入、复习、测试、词汇、Space、设置。UI 由表单、卡片、文本输入、滚动列表、快捷键和对话框组成，没有摄像头、蓝牙、音视频、传感器等复杂原生能力。旧项目运行时依赖克制（PySide6 与 FSRS），基础设施已按 database / dictionary / fsrs / llm / security 分层。

## 一、最终选型

```text
React + TypeScript + Vite
           │
        Tauri 2
      ┌────┴────┐
    macOS     Android
           │
    Client SQLite
           │
     Sync Engine
           │
     HTTP Sync API
           │
 Node + Fastify + SQLite
```

选择它而不是 Flutter / React Native / Compose 的决定性理由：

* UI 极度适合 React/CSS；
* 原生能力很少，Tauri 官方插件基本全部覆盖；
* 客户端业务、同步协议、服务端统一 TypeScript，事件协议与数据模型共享同一份类型定义；
* FSRS 有成熟 TypeScript 实现（ts-fsrs）；
* AI Coding Agent 对 React/TS/Node 的实现、调试和 UI 验收能力最强；
* React UI 可以直接在浏览器运行，把绝大多数 UI/UX 验收交给 Playwright；
* 唯一稍重的容量预测如 TS 不够快，可以非常局部地下沉 Rust，不改变整体架构。

## 三、最重要的数据架构原则

当前开发目标优先级已经明确：

> **先实现云端数据托管和同步，让真实软件尽快可以使用云端权威数据。**

第一阶段不被以下事项阻塞，以后再补：本地独立模式、DataSpace、多服务器数据隔离、Cloud → Local fork、复杂账号系统。

但客户端从第一天起保留完整 SQLite。正式语义：

```text
云端数据库  = Authority / 真理源
客户端 SQLite = 完整本地副本 + 工作数据库
React UI    = 永远直接访问客户端本地数据
```

**绝对不要做成** `React → HTTP → Server → DB`，否则本地数据库只会退化成 cache。正确形态：

```text
React
  ↓
Application
  ↓
Repository
  ↓
Local SQLite
      │
      └── Sync Engine ── HTTP ── Cloud
```

即使断网，客户端仍正常使用本地完整副本；恢复网络后继续同步。**"断网"不等于切换到本地模式。**

## 四、同步设计

Ebbinghaus 的关键优势：`learning_events` 不可变、append-only。因此**不引入** PowerSync / Zero / Electric / RxDB 等通用 local-first 数据库框架，不构建通用数据库同步系统。

第一版同步只需要：`event_id` 去重、outbox、`server_seq` 游标、push、pull、retry/backoff、settings 冲突规则。

服务端学习事件至少保留：`eventId`、`deviceId`、`deviceSeq`、`occurredAt`、`serverSeq`。

> **`serverSeq` 只是同步游标，不是领域事件实际发生顺序。** 离线设备晚上传的旧事件可能得到更大的 `serverSeq`。

领域重放必须采用独立、确定的排序规则：

```text
occurredAt → deviceSeq → deviceId / eventId tie-break
```

禁止直接按 `serverSeq` 做 FSRS 或任务状态回放。

## 五、服务器必须保持"哑"

服务器只做：鉴权、schema validation、`event_id` 去重、分配 `server_seq`、存储、增量查询、settings 存储、健康检查、备份。

禁止放入：FSRS、任务调度、DailyPlan、容量预测、词书逻辑、首过逻辑、词汇业务。业务规则全部属于客户端。

个人自用第一版无需账号系统，直接 `Base URL + Bearer access token` 配置。第一版 API 保持在此范围内：

```text
POST /sync/push
GET  /sync/pull?after_seq=1234
GET  /settings
PUT  /settings
GET  /health
```

服务器 SQLite 使用 better-sqlite3；不为这个规模引入 PostgreSQL。

## 六、开发顺序：服务器优先

不要一上来重写全部 UI。

```text
Phase 0  共享 protocol / schema
Phase 1  Node + Fastify + SQLite Server
Phase 2  最小同步客户端 / 测试 Harness：
         把现有真实学习数据真正送上云端，验证
         push / pull / 幂等 / 断线 / 恢复 / cursor / backup
Phase 3  新客户端 SQLite Repository、outbox、sync engine
Phase 4  Tauri Android 技术验收（闸门测试）
Phase 5  React UI 全面迁移
Phase 6  macOS + Android 正式 App
```

**"能让真实数据先托管在云端"比"先把新 UI 全部画完"优先。**

## 七、Tauri Android 闸门测试

不要等整个 React UI 迁完才第一次打 Android release。在大规模 UI 迁移之前做极小 PoC，只验最危险的点：

```text
1. macOS + Android 创建并迁移 SQLite
2. 批量读写 SQLite
3. 连接真实 Cloudflare Tunnel Server
4. push / pull / outbox
5. App 后台 → 前台恢复
6. 长 TextArea
7. 60 词列表滚动
8. 容量预测
9. Android release APK
```

全部通过后正式锁死 Tauri 全端。若只是某个插件有问题，优先写一个很薄的 Tauri 原生插件。只有 Tauri Android 本身出现持续性框架/生命周期/构建问题，才启动逃生路线：`macOS = Tauri，Android = Capacitor`——React、Domain、Application、Protocol、Sync 不重写。

## 八、容量预测

真实代码已是 `capacity-monte-carlo-v2`（默认约 300 samples、21 days、最多 6 个候选 List），v2 已用 base path + candidate path pool 复用消除逐候选完整重放；应用层已有 input fingerprint → memory cache → persisted DailyPlan cache，输入未变化不重跑蒙特卡洛。

迁移原则：

> **第一版纯 TypeScript 实现，不提前写 Rust。**

同时保持：固定 seed、相同算法版本、相同行为测试、相同输入 → 相同输出；**禁止用户点击"今日"时同步重跑完整预测**。推荐交互：

```text
打开今日 → 立即显示最近缓存的 DailyPlan
→ 若输入已变化则后台更新 → 完成后刷新 UI
```

若 release build benchmark 表明纯 TS 明显超过约 1 秒，再把 `CapacitySimulator` 单独下沉 Rust worker / `spawn_blocking`，必要时用 Rayon。不要把整个 domain 搬进 Rust，不要引入 CUDA/BLAS/科学计算框架——这是状态机 Monte Carlo，不是大型矩阵运算。

## 九、UI 架构必须为浏览器验收设计

硬性工程原则：

> **React UI 必须能够完全脱离 Tauri 壳，在 Vite 浏览器模式运行。**

禁止页面直接 `import { invoke } from "@tauri-apps/api/core"` 后到处调 native API。正确形态：

```text
React
  ↓
Ports / Application interfaces
  ├── BrowserTestAdapter
  └── TauriProductionAdapter
```

浏览器只替换最外层 adapter。不要为了测试产生第二套业务逻辑。

## 十、UI/UX 验收策略

日常前端开发：**约 90% 浏览器 + Playwright，最后约 10% 真实 App。**

浏览器至少覆盖：

```text
Chromium desktop   1100 × 760
Chromium compact    800 × 600
WebKit desktop     1100 × 760
Chromium mobile    Android-like viewport
```

布局、表单、主题、hover/focus、长文本、滚动、Dialog、Loading、空状态、错误状态、60 词列表、响应式、视觉回归都在浏览器完成。

真实 Tauri macOS 端使用官方推荐的 **WebdriverIO + `@wdio/tauri-service`** 做自动 E2E（支持 macOS，且可直接跑 Vite/Chrome 的 browser mode）。

Computer Use 只负责机器断言不擅长的：视觉舒适度、空间是否拥挤、实际字体、滚动体验、窗口 chrome、macOS focus、Android 软键盘、状态栏/safe area、触摸、后台恢复、真实 App 与浏览器视觉偏差。不要让 Computer Use 替代 Playwright 做大量确定性点击回归。

## 十一、明确不要做的事情

```text
不要把 server 变成业务计算服务器。
不要让 React 页面直接依赖 Tauri API。
不要为了 SQLite 性能提前写 Rust Repository。
不要把 server_seq 当领域时间顺序。
不要引入通用 local-first 数据库框架。
不要一开始解决 DataSpace / 多服务器切换。
不要在页面导航时现场重算 Monte Carlo。
不要让浏览器测试模式拥有另一份产品逻辑。
不要因为 Android 某一个 plugin 有 bug 就立刻换整个技术栈。
不要在 Tauri Android release PoC 之前迁完所有 UI。
```

## 十二、附录：同步工程要求（2026-09-09 规划会话确认）

以下口径在技术选型定稿前的规划会话中已确认，与上文共同生效：

- **秒级丝滑切换**是双端切换的目标体验；服务器网络质量一般但终端常联网，不考虑分布式与定时批处理。
- **推送**：每次产生事件的写操作后立即后台推送（单事件仅数百字节）；失败进 outbox 指数退避重试。
- **拉取**：App 启动与回到前台时无条件增量拉取一次（`since=<last_seq>`）；前台活动期先上轮询（5–10 秒），SSE 作为后续优化——弱网下轮询无状态、更鲁棒。
- **弱网传输**：单端点批量收发、gzip 压缩、增量游标断点续传，把往返次数压到最少。
- **新设备接入**：下载服务器全量事件（或快照 + 增量）后本地重放建库，不需要服务器做任何计算。
- **派生状态不同步**：FSRS 卡片、List 状态、每日计划等由各终端从同一事件集确定性重放派生；算法版本必须随事件持久化（沿袭 V1 口径）。
- **收敛性**：事件只增不改、ID 唯一、按确定规则排序，两端重放同一事件集即得到同一状态——不存在传统冲突解决，只有去重和排序。
